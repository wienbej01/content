YT‑AI Influencer System – End‑to‑End Sprint Plan
1. Context and Objectives
Recent documentation and code observations show a stark difference between the target architecture and the current state of the system. While the enhanced documentation claims a fully operational database‑driven pipeline, the cut‑over plan clarifies that the running orchestrator (produce.py) is still file‑driven and merely mirrors state into the unified production ledger. The plan further notes that produce_db.py is missing, and that the database remains a shadow rather than the execution authority. The current execution graph in produce.py diverges from the declarative STAGE_REGISTRY, and the stage adapter functions connecting the scripts to the services do not exist.
For implementers unfamiliar with the project, a separate System Context and Target Specification document (supplied alongside this plan) provides a comprehensive overview of the current system, target architecture, data model, failure modes and desired end state. Reading that document before implementation is strongly recommended to ensure a holistic understanding of the environment and the reasons behind each sprint.
To rectify the system, this sprint plan treats the cut‑over plan as the authoritative baseline. It goes further by incorporating the enhancements identified in the earlier assessment: database authority, identity split, crash‑resilient orchestration, deterministic reuse, improved creative QA, YouTube packaging and analytics, and comprehensive observability. The plan is broken into phases (sprints) with explicit tickets, deliverables, and pass‑gates. Multiple agents (software engineer, database engineer, auditor, validator, creative team, analytics engineer) are assigned to ensure holistic coverage.
Goals
    1. Make the database the single source of truth for the entire production lifecycle. No stage may read legacy JSON or manifest files; all identity, lineage, state and approval gates must be computed from the ledger.
    2. Eliminate root‑cause bug classes by splitting overloaded beat identifiers (creative_beat_id, timeline_span_id, render_unit_id, artifact_id) and deriving durations from measured audio rather than target estimates.
    3. Provide crash‑resilient orchestration with idempotent execution and no duplicate paid work, enabling resumability after any stage failure.
    4. Incorporate creative and packaging enhancements: enforce multi‑persona reviews, semantic and aesthetic QA, hook structures, and packaging design to maximise viewer retention and channel growth.
    5. Add observability and analytics: collect metrics per stage, per render unit and per deliverable; link performance data to creative and production attributes; enable controlled experimentation.
    6. Prepare the system for distributed execution: design for multi‑machine coordination and future scaling.

3. Sprint Structure and Pass‑Gates
Each sprint is roughly one to two weeks of focused work for an experienced engineer. Tickets are atomic and testable; a stage or feature is considered done only when it passes its explicit acceptance tests. Gates are defined to ensure the system’s integrity – for example, no stage may read JSON inputs, and no deliverable may proceed past an unresolved change request. Where possible, integration tests stub paid providers to avoid cost during development.
Pass‑gate definitions
    • Gate File Authority – CI test fails if any stage reads state.json, gates.json, media_plan.json, beat_timing_map.json or manifest files as live authority.
    • Gate Identity – Unit tests ensure that each entity uses the correct identifier: creative beats map to timeline spans, spans map to render units, and render units map to artifacts. No code may use beat_id as a lookup key after the split.
    • Gate Crash Resume – A crash injected after each stage must resume successfully without duplicate provider requests or duplicate outputs.
    • Gate Golden Truth – assert_all_valid() must block assembly if any clip is stale, invalid, missing or has unresolved change requests.
    • Gate Creative Approval – Human reviewers (multi‑persona or human testers) must approve script and storyboard revisions before TTS or spend is authorised. Approval is bound to an exact revision hash; any change invalidates prior approvals.
    • Gate Spend – Paid generation is gated by budget approval bound to the render‑plan SHA; any change to the plan resets the approval.
    • Gate Final Review – Final deliverables must pass technical QA and aesthetic QA; any failure opens a change request against the owning stage. A human Gate B reviewer must approve final videos.
    • Gate Publish & Analytics – Publishing requires AI disclosure and binds deliverables to YouTube uploads; analytics must capture views, CTR and retention for each deliverable.

5. Risk Management & Mitigations
Risk	Mitigation
Big‑bang rewrite temptation	Enforce strangler pattern: keep produce.py runnable until Sprint 6; flip authority gradually.
Hidden file reads	CI grep gate (OPUS‑1‑5) and auditor reviews ensure no forbidden reads.
Paid provider cost during testing	All integration tests stub ElevenLabs and Higgsfield; only one real run in Sprint 6 uses real APIs.
Identity migration breaking old projects	Migration script (OPUS‑6‑5) imports legacy projects and dual‑writes until legacy retirement.
Creative quality stagnation	Sprint 9 introduces hook templates, packaging experiments and performance attribution to provide continuous improvement.
Analytics or YouTube API changes	Abstract API calls behind services; write tests that mock responses; monitor for API changes.
Scaling complexity	Sprint 8 designs distributed execution; treat scaling as optional until single‑instance correctness is proven.
6. Definitions of Done
    1. produce_db.py is the only production entry point; produce.py is removed or a thin shim.
    2. All pipeline stages load inputs from the ledger and commit outputs as ledger revisions; JSON files are never used as authority.
    3. Identity is fully split; tests cannot use beat_id as a lookup key; multi‑slot beats, splits and slots assemble correctly.
    4. Crash injection tests pass at every stage; resumes do not duplicate paid jobs or regenerate artifacts.
    5. Creative and final QA gates block progression on unresolved change requests; approvals are bound to revision hashes; stale approvals reset automatically.
    6. At least one golden run with stubbed providers and one real run using the DB‑native pipeline succeed end‑to‑end, producing a deliverable with correct lineage and no manual intervention.
    7. A migration script imports existing projects and after migration, deleting legacy files does not break resume.
    8. Publishing, atomization and analytics integrate seamlessly; performance data is stored in the ledger and available for correlation with creative attributes.
    9. Observability dashboards and alerts exist for stage durations, failure rates, cost overruns and retention metrics.
    10. Continuous improvement processes (topic scoring, hook templates, packaging experiments, attribution analysis) feed insights back into new productions.
7. Timeline and Parallelism
Sprints 0 and 1 are sequential prerequisites. Sprint 2 (identity split) must finish before Sprints 5 and 6 but can overlap with Sprint 3 and Sprint 4 once database migrations stabilise. Sprint 7 (publish/analytics) and Sprint 8 (observability) can overlap with the latter half of Sprint 6. Sprint 9 (creative improvement) begins after at least one real run (Sprint 6) and initial analytics ingestion (Sprint 7).
This plan acknowledges that the work may exceed the original estimate of 24–34 engineering days; adding creative, analytics and observability enhancements will likely require 45–60 engineering days spread across multiple agents. However, the deliverables are structured so that a minimally viable DB‑native pipeline with stubbed providers can emerge after Sprint 6 and begin delivering videos while subsequent sprints add growth and optimisation features.
