# S9-C02 — Supersede render units on re-compile (D-015)

## Metadata
- **Ticket ID:** S9-C02
- **Title:** Mark prior render units superseded when compile_media re-runs after invalidation; consumers read only the active plan
- **Requirement / risk IDs:** R3 / D-015
- **Priority / severity:** P1 / MEDIUM
- **Risk level:** medium
- **Execution class:** COMPLEX
- **Dependencies:** none
- **Blocks:** S9-C05 (both touch `compile_render_plan`/`plan_render_units`; C02 lands the supersession contract first)
- **Wave:** 1
- **Status:** pending

## Observable outcome
After `invalidate_stages("compile_media")` + re-compile, the production has **exactly one active set of render units** for the current render-plan revision; the prior revision's units are marked `superseded` and are excluded from `generate_media`, `qa_media`, and `assemble`. Observable by: an integration test that runs compile twice and asserts the unit count for the active plan equals the span count (not 2×), and that consumers see only active units.

## Evidence and rationale
- **Observed current behavior:** re-running compile after an upstream edit produced 8 render units (4 stale + 4 new); the ledger note says assembly then saw clips=90 s vs audio=45 s.
- **Supporting paths:**
  - `scripts/production_db.py:353-368` — `invalidate_stages` sets `stage_runs.status='stale'` only; never touches `render_units`.
  - `scripts/production_repo.py:367-442` — `plan_render_units` assigns `ordinal = MAX(ordinal)+1` (always appends); never supersedes.
  - `db/migrations/001_production_ledger.sql:206-232` — `render_units` already has `status`, `parent_render_unit_id`, `slot_index`, `slot_total`, and `UNIQUE(production_id,ordinal)`. (Lifecycle columns exist — likely **no new migration needed**; confirm status values in use.)
  - `scripts/produce_db.py:482-487` — `invoke_compile_media` calls `compile_render_plan(span_specs=..., estimated_cost_usd=...)` which returns `plan_revision_id`.
  - `scripts/produce_db.py:649-657` — `invoke_generate_media` selects units `WHERE status IN ('ordered','change_requested')`. (So superseded units must NOT be 'ordered'.)
- **Confirmed root cause:** invalidation does not supersede render units; `plan_render_units` appends with fresh ordinals; consumers that select by status/revision pick up both sets.
- **Why necessary:** duplicated units double the timeline and corrupt spend/QA/assembly.

## Context capsule
- **Paths:** `scripts/production_repo.py` (`plan_render_units`, `compile_render_plan`), `scripts/production_db.py` (`invalidate_stages`), `scripts/produce_db.py` (`invoke_compile_media`, `invoke_generate_media`, `invoke_qa_media`), `scripts/assemble_db.py` (`build_assembly_inputs`), `db/migrations/001_production_ledger.sql`.
- **Key symbols:** `plan_render_units`, `compile_render_plan`, `invalidate_stages`, `render_units.status`, `parent_render_unit_id`, `render_plan` document revision.
- **Invariants:** render units are immutable history — supersede, never delete/overwrite. `UNIQUE(production_id,ordinal)` must still hold. Superseded units keep their `active_artifact_id`/history for audit.
- **Upstream:** `compile_media` consumes `timeline_spans` (status='active') + the active render_plan revision. **Downstream:** generate/qa/assemble must see one active set.
- **Convention:** one transaction per plan; fail-loud.

## Scope
- **Expected change areas:** when a new render-plan revision is created (or compile re-runs for a production), mark the prior revision's render_units `status='superseded'` and set new units' `parent_render_unit_id` to the superseded counterparts where traceable; ensure all consumers filter to active units.
- **Permitted inspection areas:** every SELECT against `render_units` (grep `FROM render_units` / `render_unit` across `scripts/`), `build_assembly_inputs`, `run_render_unit_qa`.
- **Protected:** immutability of past units (no UPDATE to ordinal/duration/artifact of existing units); gate SHA computation (`invoke_gate_a_spend` reads the active render_plan payload — `produce_db.py:497-538`).
- **Exclusions:** do not change slotting logic (S9-C05). Do not edit the real run DB.
- **Discovery (confirm before implementing):** (a) the full set of `status` values units pass through (`ordered` → … → `delivered`/`change_requested`?); pick `superseded` consistently. (b) Whether `render_units` carries a `render_plan_revision_id`/FK or only `production_id` — if no FK, supersession is "all prior active units for this production not in the new set." (c) Enumerate every consumer SELECT and confirm each filters by status/active-revision. Record findings in the ticket.
