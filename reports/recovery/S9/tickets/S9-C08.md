# S9-C08 — Eliminate module-level PRODUCTION_DB_PATH override (test-isolation defect)

## Metadata
- **Ticket ID:** S9-C08
- **Title:** Remove the module-level `PRODUCTION_DB_PATH` env override in `test_produce_db_orchestrator.py`; scope DB env to a fixture like every other test
- **Requirement / risk IDs:** R8 / D-017
- **Priority / severity:** P2 / MEDIUM (test reliability — undermines the suite the sprint validates against)
- **Risk level:** low–medium
- **Execution class:** COMPLEX
- **Dependencies:** none
- **Blocks:** none
- **Wave:** 1
- **Status:** pending

## Observable outcome
The full suite is order-independent: every test passes regardless of collection order, and no test leaves a process-global `PRODUCTION_DB_PATH` value that can change another test's database. Concretely, running `tests/test_produce_db_orchestrator.py` immediately before `tests/e2e/test_s8_projections_resume.py` (the order that currently fails) passes, and the full suite stays green. Observable by: a regression test / CI order check that runs the polluting combination and asserts pass; a grep/assertion that no test module sets `PRODUCTION_DB_PATH` at module import scope.

## Evidence and rationale
- **Observed current behavior:** the `s8_resume` e2e test fails with `Stage 'reconcile_timing' failed: No active timeline spans for production …` **only when run after `test_produce_db_orchestrator`** in the same session. It **passes in isolation** (verified: 1 passed, ~36 s, both at clean baseline `3f1c9fa` and with S9-C01 applied). The failure is therefore a cross-test isolation break, not a production-code defect.
- **Supporting paths / the anomaly:**
  - `tests/test_produce_db_orchestrator.py:16-19` —
    ```
    TEST_DB = ROOT / "db" / "test_produce_db.db"
    os.environ["PRODUCTION_DB_PATH"] = str(TEST_DB)   # MODULE-LEVEL — no teardown
    ```
    This is the **only** module-level (top-level) `PRODUCTION_DB_PATH` assignment in the suite. `grep -rn 'os.environ\["PRODUCTION_DB_PATH"\]' tests/` shows **every other** occurrence (test_repair_routing_lb603, test_sprint5_tts_service, test_sprint8_publish, test_sprint2_production_repo, test_diagnostic_audio_lb401, test_sprint7_assemble_db, test_sprint4_authoring, test_sprint6_media_service, test_sprint3_stage_runner, e2e/test_crash_matrix, test_sprint9_migrate) is **inside an autouse fixture paired with a `del os.environ[...]` teardown**.
  - `tests/conftest.py:28-40` — the canonical isolation pattern: autouse `_isolate_production_db` uses `monkeypatch.setenv` (auto-restored) **plus** `production_db._db_path_override` (reset to `None` on teardown). A module-level `os.environ[...] = …` with no teardown is inconsistent with this and is the prime suspect for leaking DB identity across tests.
- **Confirmed:** the failure reproduces at clean baseline (`3f1c9fa`, S9-C01 changes stashed) in the same batch order — so it is **pre-existing and independent of S9-C01**.
- **Root-cause caveat (IMPORTANT):** the isolation mechanism is subtle (conftest monkeypatches per test, so the leaked env *should* be reset per test). The module-level override is the **evidenced prime suspect** but is **not yet proven** to be the sole cause — another `test_produce_db_orchestrator` side-effect (e.g. a shared real-FS `db/test_produce_db.db` or a `_db_path_override` interaction) could contribute. **Reproduce and isolate the actual cause before fixing** (see steps).
- **Why necessary:** the sprint's validation rests on a trustworthy suite; an order-dependent failure both masks real regressions and can produce false failures. The user requires real, reliable tests (no leakage).
